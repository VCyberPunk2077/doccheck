# Архитектура DocCheck

На срезе `main` `4e59e9656d7f2c44a38495571e756a618bda22d0` локальная установка
принимает КФЗ и первичные документы, хранит задание и выдаёт состояние,
сохранённый результат, источники и XLSX. Документный worker можно запустить
с отдельно предоставленным адаптером. Рабочий `process_package`, который
извлекает значения из загруженной КФЗ и первички и выполняет финансовую
сверку, в этой версии не подключён. [Сценарий и открытые вопросы](case/README.md)

## Компоненты и хранилища

| Компонент | Ответственность |
| --- | --- |
| [React/Vite](../frontend/README.md) | Мастер выбирает КФЗ и первичные документы. История показывает сохранённые запуски, а экран результата отображает состояние задания, таблицу сверки и источники. UI получает суммы из API строками и различает ноль и отсутствующее значение. |
| [FastAPI](../backend/src/doccheck_backend/api.py) | Принимает multipart, проверяет пакет и параметры, сохраняет оригиналы и ставит задание в очередь. Отдельные маршруты читают историю, состояние, результат и источники и выдают XLSX. HTTP-запрос на загрузку заканчивается после сохранения, до обработки документов. |
| [PostgreSQL и Alembic](../backend/README.md) | Миграции подготавливают таблицы. База хранит задания, манифест с ID, форматом и SHA-256, технические ошибки и сохранённый результат. Синтетические задания каркаса используют свою таблицу. |
| [Хранилище оригиналов](../backend/src/doccheck_backend/uploads.py) | Файлы записываются в каталог запуска под серверными ID. Локальный Compose использует том `run-files`, а документный worker подключает его только для чтения. При выдаче оригинала или фрагмента API проверяет принадлежность пакету и сверяет SHA-256 фактических байтов с манифестом. |
| [Python worker](../backend/src/doccheck_backend/run_worker.py) | Отдельный процесс резервирует документное задание в PostgreSQL, вызывает явно настроенный `module:callable` и сохраняет терминальный `CheckJob`. Очередь обрабатывается последовательно. По умолчанию Compose запускает worker синтетических заданий, а профиль `document-worker` включает эту очередь при наличии адаптера. |

```text
КФЗ и первичные документы → React → FastAPI → PostgreSQL: queued
                                      │
                                      └──→ локальный том оригиналов

PostgreSQL: queued → документный worker → явно подключённый адаптер
                                      │                 │
                                      └── читает том    └──→ CheckJob → PostgreSQL

PostgreSQL: сохранённый результат → FastAPI → React: таблица, источники и XLSX
```

## От пакета к сохранённому отчёту

1. `POST /api/v0/runs` принимает КФЗ и первичку. Повтор пакета с тем же
   ключом идемпотентности возвращает тот же запуск. Совместимый клиент
   может указать номер договора, границы периода и адрес строки КФЗ
   единым комплектом. Без этих полей область должен определить адаптер.
   Схема результата v1 хранит одну область для загруженной КФЗ.
   [HTTP-контракт v0](../contracts/doccheck-api.v0.openapi.yaml)
2. Worker передаёт адаптеру манифест, область при наличии и локальное
   расположение файлов. Перед сохранением worker проверяет контракт
   результата, ID запуска и документов, соответствие заявленных в
   результате хешей и форматов манифесту, выбранную КФЗ и совпадение
   явно заданной области. Следующий запуск worker помечает
   прерванное задание ошибкой и продолжает очередь.
   [Режим запуска и проверки worker](agent-runs/nrt-95-worker-runtime.md)
3. UI запрашивает состояние через `GET /api/v0/runs/{run_id}`, затем
   сохранённый `CheckResult` через `GET /api/v0/runs/{run_id}/findings`,
   если обработка завершилась с результатом. Панель источника открывается
   справа по выбранному доказательству. Структурный фрагмент относится
   к указанному документу того же запуска. Оригинал выдаётся отдельно.
   PDF можно открыть на указанной
   странице. Для PNG интерфейс рисует рамку после загрузки изображения
   при наличии валидного `bbox`. Связь рамки с реквизитом должен
   подтвердить адаптер. Для XLSX и DOCX виден
   структурный адрес и доступно скачивание оригинала. Экспорт XLSX
   формируется сервером из сохранённого результата и содержит итоги,
   ID и адреса источников. [Чтение результата](../backend/src/doccheck_backend/run_reads.py)
   · [Экспорт XLSX](../backend/src/doccheck_backend/run_xlsx.py)

Маршруты React Router открывают мастер по `/` и `/checks/new`, историю
по `/checks`, таблицу и состояние запуска по `/checks/:id`. У результата
есть отдельные разделы по `/checks/:id/documents`, `/checks/:id/exceptions`,
`/checks/:id/conclusion` и `/checks/:id/log`. Общий журнал открывается по
`/log`, проверка сервисов по `/system-status`.
[Маршруты frontend](../frontend/src/app/App.tsx)

В результате видны вкладки «Результат» и «Документы». Первая показывает
сводку, таблицу и заключение с раскрытием доказательств по строкам. Вторая показывает документы и основания решений по ним.
Панель источника открывает сохранённое доказательство из строки или её
слагаемого. Полноэкранный режим сверки и панель возвращают фокус после
закрытия. Экспорт XLSX доступен для сохранённого результата. Готовый
синтетический пример показывает адреса из встроенного результата.
[Перенос экрана сверки, PR #71](https://github.com/VCyberPunk2077/doccheck/pull/71)
· [Проверки интерфейса](agent-runs/nrt-107-result-parity.md)

## Изменения в открытых PR промпта №3

[PR №83](https://github.com/VCyberPunk2077/doccheck/pull/83) возвращает форму
в состояние новой отправки после HTTP 202. Для истории используется тот же
`GET /api/v0/runs`, с необязательным фильтром по сохранённым счётчикам.
Отображение состояния задания не определяет статусы строк.

[PR №82](https://github.com/VCyberPunk2077/doccheck/pull/82) добавляет к
`GET /findings` точную сводку известных денежных значений КФЗ при наличии
классификации строк. Документы, доказательства и ошибки читаются из того же
`CheckResult`. Версии, архив и кеш описаны в
[продуктовых решениях](product-decisions.md).

## Путь бухгалтерского значения

### Реализованные компоненты

1. Переданный модуль идентификации принимает подготовленные наблюдения,
   сверяет исходник по хешу и возвращает кандидатов, фрагменты и диагностику.
   В backend есть нормализация договора, дат и периодов и проверка
   контрольных цифр ИНН. [Модуль идентификации](ml-module-boundary.md)
2. NRT-32 связывает готовое наблюдение с манифестом задания. На входе —
   переданные стадией извлечения формат, SHA-256 прочитанных байтов и адрес
   оригинала. На выходе — устойчиво адресуемое `Evidence` с исходным и
   нормализованным значениями или связанная с документом диагностика.
   [Привязка наблюдений](agent-runs/nrt-32.md) · [Контракт адресов](result-source-contract.md)
3. `plan_byte_duplicates` готовит исключения побайтовых копий внутри одного
   запуска по проверенным SHA-256. При совпадении с КФЗ она остаётся
   основным экземпляром. Функция возвращает план, применение решений
   к пакету остаётся за рабочим адаптером. [Дубли файлов, PR #49](https://github.com/VCyberPunk2077/doccheck/pull/49)
4. `Calculation.admitted_sum` точно складывает уже допущенные слагаемые
   одной единицы. При неполном или неизвестном покрытии доступна только
   наблюдаемая сумма. `compare_admitted_values` принимает сопоставимость
   и полноту как входы, сравнивает КФЗ с полной ожидаемой суммой и
   возвращает статус с дельтой либо `unverified` с `null`.
   [Сумма допущенных слагаемых](agent-runs/nrt-26-admitted-sum.md) · [Сравнение](agent-runs/nrt-29-exact-comparison.md)
5. `build_summary` группирует рассчитанные строки по статусам, полноте
   и основанию, учитывает решения по файлам и сохраняет первичные
   замечания со ссылками на доказательства и ошибки.
   [Сводка рассчитанных строк](agent-runs/nrt-35-summary.md)
6. В сохранённом результате UI показывает формулу, суммы, условия допуска и
   адресные доказательства каждого слагаемого. При открытии панели браузер
   автоматически запрашивает оригинал и адрес выбранного доказательства.
   Скачивание оригинала и открытие PDF в браузере доступны отдельными
   действиями. XLSX экспортирует
   итоговый результат проверки. [Доказательства слагаемых в UI](agent-runs/nrt-31-component-sources.md)

### Подключение рабочего конвейера

Рабочий адаптер должен связать в документном worker всё движение пакета.
Сначала прочитать файлы и сделать OCR нужных страниц, определить строку
КФЗ и подготовить наблюдения с проверенными адресами. Затем нормализовать
значения, установить договор, период и статью для слагаемых, обработать
дубли и другие исключения по согласованным правилам, определить полноту и
передать допущенные слагаемые в расчёт. Контракт сохраняет частичную сумму
и доказательства, когда полная ожидаемая сумма неизвестна.

Возможные причины расхождений требуют проверяемого основания и показываются
как гипотезы. Формат и необходимость отдельного файла промежуточной сводки
не утверждены. Нужны подключение штатного адаптера и подтверждённый прогон
с сохранением результата и выводом в интерфейс.
[NRT-95](https://linear.app/andreiakimov/issue/NRT-95/podklyuchit-ml-adapter-k-worker-i-sohraneniyu-rezultata)
· [NRT-43](https://linear.app/andreiakimov/issue/NRT-43/skvoznaya-integraciya-i-knopka-demo)

Состояние задания `queued / processing / completed / completed_with_issues /
failed` сообщает о работе очереди и сохранении результата. На уровне файла
`parse_status` описывает чтение (`pending / parsed / partial / error`),
а `decision` хранит решение об использовании
(`include / exclude / needs_review / parse_error`) и его основание.
Ошибки чтения перечисляются отдельно.

Для показателя и `verified`, и `discrepancy` требуют подтверждённых
сопоставимых значений и полного покрытия по правилам. При `verified`
дельта равна нулю, при `discrepancy` она ненулевая. При недостатке
доказательств, в том числе когда видна только частичная разница,
возвращается `unverified` с дельтой `null`. Доступные значения и
источники сохраняются. [Контракт результата](result-source-contract.md)

## Локальная установка и публичный пример

Локальный контур использует Python, PostgreSQL и файловое хранилище.
При штатном Compose фронтенд опубликован только на loopback. Для запуска
сначала нужны зависимости, миграции и пароль БД. Для документного worker
нужен образ, в котором установлен локальный доверенный адаптер. Рабочий
OCR, готовые веса, GPU, офлайн-прогон и реальная финансовая сверка ещё
требуют подтверждения. [Команды установки и запуска](../backend/README.md)

В публичной конфигурации Vercel/Render документный API закрыт, а интерфейс
открывает встроенный, явно помеченный синтетический результат. Отдельный
синтетический процесс может показать жизненный цикл задания на PostgreSQL.
Готовность облачного деплоя проверяется отдельно от этой схемы.
[Конфигурация и границы публичного режима](agent-runs/nrt-108.md)

Рабочие оригиналы и результаты хранятся вне Git. Исключение `data/` из Git
и разные worktree не ограничивают чтение файлов агентом с доступом к той же
среде. Закрытые данные, OCR-текст и независимый эталон остаются в
разрешённой локальной среде. В публичном сценарии используются только
синтетические данные. [Политика доступа и хранения](data-policy.md)

Описание сверено с указанным срезом `main`. Сверка владельцами интеграции
и обработки и предметная приёмка остаются в
[NRT-47](https://linear.app/andreiakimov/issue/NRT-47/arhitektura-po-fakticheski-realizovannomu-resheniyu).
