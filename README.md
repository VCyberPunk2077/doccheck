# DocCheck

Цель проекта — локальная сверка карточки фактических затрат (КФЗ) с первичными документами: сбор сводных значений, сравнение с КФЗ и показ источников и возможных причин расхождений.

Проект команды **«Буткемперы»**, хакатон МФТИ, трек 5.

## Текущий этап

На странице `/system-status` можно проверить связку frontend, FastAPI,
PostgreSQL и отдельного worker на синтетическом задании. В
[мастере проверки](frontend/README.md#загрузка-и-история-проверок) бухгалтер
выбирает КФЗ и первичные документы. API сохраняет пакет, открывает запись
в очереди и отдаёт статус и историю. При штатном запуске Compose пакет
остаётся «В очереди» (`queued`). Выделенный обработчик документов
подключается отдельно и определяет область сверки.

Для завершённого задания с сохранённым результатом доступны таблица
сверки, адреса доказательств, оригиналы и экспорт XLSX на вкладке «Документы».
Отдельная ссылка в мастере открывает готовый синтетический пример без
загрузки файлов. Подключение рабочего адаптера относится к NRT-95,
сквозная проверка с интерфейсом — к NRT-43. Переданный [Python-модуль реквизитов
и Qwen-reader](backend/ml_module/README.md) обрабатывает готовые наблюдения.
Настройку API, БД и worker описывает [backend README](backend/README.md).

## Начало работы

```sh
git clone https://github.com/VCyberPunk2077/doccheck.git
cd doccheck
```

```sh
git diff --check
```

Для приватного репозитория владелец выдаёт участникам доступ; каждый проверяет клонирование под своим аккаунтом. Успешное клонирование владельцем не подтверждает доступ остальных участников.

## Планируемый стек

Frontend: React, TypeScript, Vite, React Router, Zustand, Tailwind CSS и собственные компоненты. Менеджер пакетов — pnpm. Backend: Python/FastAPI, SQLAlchemy, Alembic, отдельный Python worker и PostgreSQL. Миграции создают таблицы заданий. Оригиналы сохраняются локально, а PostgreSQL хранит задания, метаданные и результаты.

## Запуск каркаса через Docker Compose

Нужны запущенный Docker Engine с Linux-контейнерами и Docker Compose с
поддержкой `up --wait`. Скопируйте `.env.example` в `.env`, если файла ещё
нет, и задайте `DOCCHECK_DB_PASSWORD` случайной строкой из букв и цифр,
например 32 шестнадцатеричными символами. Затем из корня репозитория:

```sh
docker compose up --build --wait
```

Откройте [http://127.0.0.1:8080](http://127.0.0.1:8080) для мастера
загрузки. Ссылка «Проверка системы» открывает `/system-status`, где
можно создать синтетическое задание. Текущие сценарии описаны в
[frontend README](frontend/README.md).
Если порт занят, задайте `DOCCHECK_PORT` в `.env`.
PostgreSQL проходит проверку готовности, затем отдельный сервис `migrate`
применяет миграцию перед запуском API и worker.

```sh
docker compose ps --all
docker compose down
docker compose up --wait
```

Обычный `down` сохраняет задания в именованном volume PostgreSQL.
`docker compose down --volumes` удалит данные этого проекта. Первичная
сборка получает закреплённые образы и зависимости из реестров. GPU, OCR и
реальный inference относятся к оставшейся части NRT-41.
Подробности конфигурации и версии — в [документации backend](backend/README.md).

## Границы проверенного окружения

[Compose CI](https://github.com/VCyberPunk2077/doccheck/actions/runs/43517413330)
проверил дерево коммита `71827eea222cfef60396ab9fa2016e348e8ac840`
на Linux/amd64 с Docker Engine 29.4.2. Прогон изолированной базы применил
миграции, проверил готовность сервисов, выполнил синтетическое задание
из браузера и подтвердил сохранение результата после остановки и повторного
запуска. В этом прогоне сборка и старт заняли 30 с, повторный запуск
без сборки — 13 с. Это замеры каркаса на CI. Минимальные CPU, RAM и место
на диске для рабочей сверки ещё не измерены.

- **Подготовка.** Первичная сборка получает базовые образы и зависимости из
  реестров. [Версии, лицензии и настройка PostgreSQL](backend/README.md#docker-compose)
  описаны в backend README. Готовые веса и зависимости адаптера
  [подготавливаются отдельно](backend/ml_module/README.md#подключение-готовых-весов-для-inference).
- **Запуск.** PostgreSQL хранит задания и результаты в томе
  `postgres-data`. Оригиналы хранятся в отдельном томе `run-files`.
  API и процессы обработки используют локальную БД внутри Compose.
  Профиль [`document-worker`](backend/README.md#отдельный-документный-worker-в-compose)
  требует отдельного образа с установленным доверенным адаптером и указания
  `DOCCHECK_DOCUMENT_PROCESSOR`. Офлайн-установка и работа реального адаптера
  без внешней сети пока не подтверждены.
- **Приёмка.** [Архитектура DocCheck](docs/architecture.md) описывает
  границы уже работающих компонентов. В [двух сценариях сверки](docs/case/use-cases.md)
  указаны входы и ожидаемые результаты для синтетических пакетов.
  [Отчёт о чистом запуске](docs/agent-runs/nrt-45-clean-start.md) фиксирует
  проверенный синтетический запуск и ограничения среды. Сквозной прогон
  обоих сценариев с рабочим адаптером и чистый запуск такого контура
  на релизной версии предстоит подтвердить.
